# 天体详情三维模型性能

## 2026-09-06：界面线程与模型计算分离

原实现虽然异步创建 PixelMap，但创建前的纹理双线性采样、球面光照、星环遮挡和程序化粒子绘制都是 ArkUI 线程上的同步逐像素循环。展开 640×640 模型或连续拖动时会阻塞同线程触摸、滚动和过渡动画。

当前设计：

- `DetailModelRasterizer.ets` 保留原像素算法，`DetailModelWorker.ets` 在独立线程计算；ArkUI 只提交视角/光照快照并异步创建 PixelMap。
- 每个模型生命周期复用一个 Worker，第一次发送纹理和粒子，后续只发送矩阵、尺寸、缩放和光照；输出 ArrayBuffer 转移回主线程，不重复拷贝。
- 最多一个执行中的帧和一个合并后的待处理请求；拖动期间保留最新旋转，抬手保留最终高质量帧。不积压所有中间手势帧。
- 切换目标/清理详情时销毁 Worker、取消待处理 Promise；生成代号同时保护 Worker 结果与 PixelMap 异步回调，旧目标不能覆盖新目标。异常和 30 秒超时反馈现有失败状态，可显式重试。
- 渲染忙标志不再作为每帧变化的 ArkUI 状态；首帧使用已有准备状态，旧图保留至新帧完成。
- 保持原有稳定内嵌 320、全屏 640、交互 224 像素尺寸，没有降低纹理分辨率、星图分辨率、粒子数量或光照质量。内嵌模型任意方向旋转、两侧阅读留白不变。
- 剔除透明背景计算：纹理球体只遍历球面覆盖行及列；程序化球体/类星体只遍历其可见包围范围，循环不变量移到循环外。输出缓冲仍为完整尺寸，所有原像素哈希保持一致。

`getObjectModelView` 新增 `renderer=worker`、`computeMs`、`pixelMapMs`、`totalMs`：分别为工作线程像素计算、主线程收到像素至 PixelMap 完成、提交至完成的毫秒数。`totalMs` 包含线程启动/消息投递/调度，不是纯计算耗时；这些字段不等于星图 FPS。

`uiPulseCount` / `uiMaxDelayMs` 是计算期间主线程 16ms 定时探针的执行次数/最大超期。只在任务进行中启用，完成、取消、超时均清理。应用进入后台时停止探针及超时计时，回前台恢复，避免系统挂起 Worker 后被误报为渲染超时。它用于区分“后台模型计算耗时”与“主线程被堵住”，不是显示帧率或触摸延迟测量，系统负载也可能使超期增加。

## 构建与验证

- 同步脚本复制四个模块，并在生成工程的 **entry 模块级** `build-profile.json5` 中登记 worker 路径；不修改应用级配置或签名。重复同步幂等；遇到已有但不包含此 Worker 的 sourceOption 拒绝覆盖，需合并 workers 列表。
- `scripts/test-ohos-model-worker.mjs` 验证纹理和光照像素一致性、缓存一次、多帧复用、取消、异常、重试和旧线程消息隔离。
- `scripts/fixtures/detail-model-render-hashes.json` 来自本轮改动前的同步渲染器，9 组完全相同输入覆盖球体、星环、自发光、无光照资料、恒星、类星体、脉冲星、球状/疏散星团；比较每个输出字节的 SHA-256，而非只比图像大小。
- 继续运行模型手势/边缘滚动与三维模型 CLI 真机回归；实测记录在本轮 CHANGELOG。
- `scripts/test-ohos-model-performance-pad.py` 通过 CLI 对月球、土星、木星各完成四次 640 像素旋转，检查计算期间 UI 探针仍执行、关闭保留姿态及连续选星最终目标隔离；恢复原选中对象和时间速率。

## 官方依据

通过华为开发文档 MCP 查阅 [Worker 简介](https://developer.huawei.com/consumer/cn/doc/harmonyos-guides/worker-introduction) 与 Worker API：计算密集任务移出主线程；复用工作线程，显式管理销毁；线程文件需配置打包；Worker 不使用 AppStorage 或 UI 对象。当前 Worker 仅导入纯计算模块及消息协议，无运行时联网。

## 性能边界

本轮消除的是模型计算抢占界面线程，并减少透明区无效计算；模型仍是 CPU 离屏渲染，不声称已达到 60fps。复杂粒子模型的 640 像素首帧仍可能需要数百毫秒，但这段时间不再要求界面等待像素循环。后续如果需要全分辨率持续高帧率，应在同一参数协议下替换 GPU/原生数值后端，不能用降低分辨率、粒子数或伪装画面旋转代替优化。
