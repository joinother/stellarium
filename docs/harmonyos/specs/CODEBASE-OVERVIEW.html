2. Qt/C++ 工程师知识地图 ↑ 目录

本章面向 C++/Qt/嵌入式背景读者：不需要先学 ArkTS，用你已有的知识直接定位每个概念。

一句话心智模型：你原有的整个 Qt/C++ 应用被交叉编译成一个 41 MB 的 libstellarium.so，几乎原样； 「移植」的本质是给它造一个系统级宿主外壳——ArkTS 应用负责界面与生命周期，通过 NAPI 桥把 触摸/设置/查询翻译成 358 条 JSON 命令 喂给引擎，再把引擎渲染的 OpenGL ES 帧贴回屏幕。

2.3 ArkTS 60 秒速览（QML 对照）

QML（你熟悉）
Rectangle {
  width: 200
  property int count: 0
  Text { text: "Hi " + count }
  MouseArea {
    anchors.fill: parent
    onClicked: count++
  }
}
ArkTS（本工程壳层）
@Component
struct Greeting {
  @State count: number = 0

  build() {
    Text(`Hi ${this.count}`)
      .fontSize(20)
      .onClick(() => {
        this.count++
      })
  }
}
  • ArkTS = TypeScript 严格子集：编译期直接拒掉 any、对象字面量类型等——相当于语言级 -Werror。
  • struct + build() ≈ 一个 .qml 文件；@Entry ≈ 可加载页面；@State ≈ 绑定源，改动自动刷新视图。
  • 本工程全为 V1 体系（@Component/@State/@Provide/@Link；主窗口文件近千处状态装饰器）。
  • 读码顺序：ApplicationRoot.ets → MainWindowNativeNode.ets 的 build() → 按面板/功能跳转；契约类型集中在 StellariumTypes.ets。

2.4 移动端框架三件套（嵌入式世界没有的概念）

① 生命周期托管

系统随时创建/冻结/回收应用；onCreate / onForeground / onBackground 是系统回调而非事件循环。 本工程：隐私门控贯穿启动全程（§5）。

② 沙箱与权限

应用文件系统隔离（/data/storage/el1/bundle 只读）；危险权限须在 module.json5 声明 + 运行时弹窗。 本工程：隐私弹窗未同意前，引擎不许初始化。

③ 签名与分发

HAP 必须签名才能装真机；本工程只能用 DevEco 自动签名；上架需过商店审查（体积、权限、隐私声明）。 本工程：681 MB 体积是审查重点（见 release/ 文档）。

1

2
窗口与页面 — preparePrivacyHostPage() → getMainWindow() → new QtWindowStageAdapter(...) → loadContent('pages/ApplicationRoot')（全程只加载一次）

5

6
Qt 上下文 — [privacy-probe] qt-context-init-start 平台插件加载 /data/storage/el1/bundle/libs/arm64/libstellarium.so → QAbilityStage 转交成功
7
首帧 — StelRootItem paint reached、zero-copy frame bridge resolved、startOhosRenderPump entered
8
命令桥上线 — ArkTS 轮询 command('getAppState') 直到 bridge resolved；此后命令经 ohosDrainCommandQueue 在 Qt 线程逐帧排空

6. 命令桥契约（libentry.so） ↑ 目录

6.1 对外导出（cpp-source/types/libentry/index.d.ts）

6.2 一次调用的旅程

1 ArkTS 壳command('getSelectedObjectInfo', '{}')
→
2 libentry.so（NAPI）同步调用；dlsym 取 StellariumOhos_command
→
3 libstellarium.soQt 主线程执行命令，拼 JSON 结果
→
4 回包原路返回；ArkTS 解析为 StellariumBridgeResponse

6.3 加载策略：必须 RTLD_NOLOAD（最容易踩的坑）

void* handle = dlopen("libstellarium.so", RTLD_NOW | RTLD_NOLOAD);   // 只查"已加载"的库
if (!handle) return nullptr;   // 未就绪 → 由 ArkTS 侧重试
command = dlsym(handle, "StellariumOhos_command");
引擎未加载 → 返回 {"ok":false,"error":"bridge not available"}ArkTS 侧稍后重试（启动期轮询 getAppState）
已加载 → dlsym(StellariumOhos_command)Qt 主线程执行 → JSON 回包
为什么必须 RTLD_NOLOAD：若在 ArkUI 线程主动 dlopen 首次加载，会与 Qt 平台插件的 makeQtThreadWithMainFuncLauncher 抢占主线程上下文，触发 Qt API was likely used before Qt initialization. Aborting. → 进程 SIGABRT。

6.4 调用语义

行为说明
本地短路命令getPresentationState 由桥直接应答（不进 Qt），用于判断首帧是否就绪
静默命令dragView / zoomBy / panBy / setGyroView 不写日志，避免拖动期间与 UI 线程争用

11. 关键约束与常见坑 ↑ 目录

约束 / 坑后果与做法
必须构建 build/libstellarium-harmonyos/在 harmonyos/ 里跑 hvigor 会报 Path not found …/harmonyos/entry（镜像没有 entry 模块）
modelVersion 必须两处一致oh-package.json5 与 hvigor/hvigor-config.json5 同为 26.0.0，否则 IDE 直接报错
签名只能由 DevEco 自动签名产生自签（OpenHarmony CA）会被真机拒绝：code:9568257 fail to verify pkcs7 file
ArkUI 线程不得抢先 dlopen 引擎触发 Qt API was likely used before Qt initialization. Aborting.；只允许 RTLD_NOLOAD 查找（§6）
星图触摸不能挂全屏 UI 父会吞掉子组件 onClick；用专属触摸面（§7）
HAP 内 Qt 依赖名不能是构建树路径CPM 依赖无 SONAME 时 DT_NEEDED 写成 _deps/…，装机后 dlopen 失败；需等长改写并补齐 libmd4c/md4c-html/nlopt
资源树缺失 = Qt 拒绝启动Startup resources are incomplete…（§8）
DevEco 开着时构建加 --no-daemon否则常驻 daemon 接管任务并报 spawn java ENOENT
模拟器是 x86_64，应用是 arm64Windows 模拟器跑不了星图（Qt 无 x86_64 目标）；只能验 ArkUI 外壳（abiFilters 加 x86_64）
真机启动需解锁并保持亮屏开发者模式下系统不允许自动解锁：aa start 返回 10106102
