# 天文事件通知类型目录与文案模板设计

> **创建日期：2026-10-14**
> **状态：设计稿（未实施）**
> **关联文档：** `research/NOTIFICATION-AND-FORM-ROADMAP.md`（能力边界、数据契约与 `NotificationSchedule` 本地提醒契约）

---

## 1. 背景与目标

当前通知与提醒链路（`AstronomyNotificationService.ets`、`AstronomyReminderService.ets`）已经打通授权查询、代理提醒注册和节气一次性提醒，但事件类型维度仍然只有单一的 `kind: 'astronomy'`。要把"用户订阅某一类天象 → 本地计算 → 可见性过滤 → 按模板生成文案 → 注册系统提醒"这条链路做成可扩展的产品能力，需要先回答三个问题：

1. 一共有哪些值得通知的天文事件类型？
2. 每种类型的文案应该按哪些维度变化？
3. 哪些事件对当前观测者不可见、不该提醒？

本文档给出一份完整的事件类型目录（第 2 节）、文案模板维度规范（第 3 节）、可见性过滤规则（第 4 节）和与现有代码的对接方案（第 5 节）。所有计算保持离线，复用现有 C++ 命令桥，不引入 Push、后台网络刷新或新的设备标识读取。

---

## 2. 事件类型目录

### 2.1 设计原则

- **类型即订阅单元**：用户按类型（或类型组）订阅/退订，设置页不出现"全部通知"一个总开关以外的第二层模糊开关。
- **全球事件与本地事件分离**：日月食、至点分点是全球事件；"月升时的月食""本地可见的流星雨峰值"是本地事件。目录中用变体（variant）表达这种差异，而不是新建类型。
- **变体属于类型**：每种类型携带 0～N 个变体标签，变体决定文案模板选择，不参与订阅判断——用户订阅"月食"，不需要分别订阅"月食（全食）"和"月食（偏食）"。

### 2.2 类型清单

类型 ID 采用小写中划线格式，与 `research/NOTIFICATION-AND-FORM-ROADMAP.md` 中 `AstronomyEventKind` 的命名风格一致。

#### A. 日食与月食

| 类型 ID | 说明 | 变体 |
| --- | --- | --- |
| `solar-eclipse` | 日食 | `total`、`partial`、`tomorrow`（次日发生） |
| `lunar-eclipse` | 月食 | `total`、`partial`；时刻变体：`soon`（临近）、`tonight`（今晚）、`at-moonrise`（月升时即已进行）、`after-moonrise`、`rising`（带食而升）；`max`（食甚） |

日月食是全目录中文案变体最丰富的类型：食的分类（全/偏）、时间关系（临近/今晚/次日）、与月升的关系（月升前已开始、月升时进行中、带食而升）三个维度正交组合，模板选择逻辑见第 3.2 节。

#### B. 至点与分点

| 类型 ID | 说明 | 变体 |
| --- | --- | --- |
| `march-equinox` | 春分 | `north`、`south`（半球） |
| `june-solstice` | 夏至 | `north`、`south` |
| `september-equinox` | 秋分 | `north`、`south` |
| `december-solstice` | 冬至 | `north`、`south` |

同一天文时刻在两个半球的意义相反（北半球夏至 = 南半球冬至）。四类二十四个半球变体保证文案准确；结合本项目已实现的二十四节气计算，北半球文案可优先关联"夏至/冬至对应节气"表述。

#### C. 月相

| 类型 ID | 说明 | 变体 |
| --- | --- | --- |
| `new-moon` | 新月 | — |
| `full-moon` | 满月 | `general`（通用）、`rise`（满月升起时刻） |
| `supermoon` | 超级月亮 | `general`、`rise` |

`general` 与 `rise` 是全目录通用的呈现变体：前者回答"今晚有什么"，后者回答"几点升起、去哪看"。用户在规则中按类型订阅后，呈现变体由提前量（leadMinutes）和事件形态自动决定，不需要单独订阅。

#### D. 行星动态

| 类型 ID | 说明 | 变体 |
| --- | --- | --- |
| `max-elongation` | 大距 | `east`（东大距，昏后可见）、`west`（西大距，晨前可见） |
| `planet-opposition` | 冲日 | — |
| `perihelion` | 过近日点 | — |
| `aphelion` | 过远日点 | — |

大距的东西变体直接决定晨昏文案：东大距的天体日落后西方低空，西大距的天体日出前东方低空。

#### E. 流星雨与彗星

| 类型 ID | 说明 | 变体 |
| --- | --- | --- |
| `meteor-shower` | 流星雨 | 峰值时刻与本地月相干扰情况写入文案数据，不作为变体 |
| `comet-brightest` | 彗星达到最亮 | — |

#### F. 合相

| 类型 ID | 说明 | 变体 |
| --- | --- | --- |
| `conjunction-moon-planet` | 月合行星 | `morning`、`night`（发生时段） |
| `conjunction-moon-star` | 月合恒星 | `morning`、`night` |
| `conjunction-planet-planet` | 行星合行星 | `morning`、`night` |
| `conjunction-planet-star` | 行星合恒星 | `morning`、`night` |

合相的晨/夜变体与位置数据共同生成"黎明东方低空""入夜后西方天空"这类方位文案。

#### G. 卫星

| 类型 ID | 说明 | 变体 |
| --- | --- | --- |
| `satellite-pass` | 卫星过境 | `iss`（国际空间站）、`bright`（明亮过境/闪光） |
| `satellite-transit` | 卫星凌日/凌月 | — |

卫星类是唯一有明确开始/结束时刻的类型，是实况窗（Live View）能力的候选场景，同时必须遵守既有约束：TLE 历元过期即停止可靠过境提醒并标示原因。

### 2.3 类型目录汇总

以上共 22 个类型 ID、约 40 个类型×变体组合，覆盖日月食、分至点、月相、行星动态、流星雨、彗星、合相和卫星八大类。相比 `research/NOTIFICATION-AND-FORM-ROADMAP.md` 中 7 值的 `AstronomyEventKind` 基线，本目录是超集；实施时建议保持旧值兼容，新增值按本目录命名。

## 3. 文案模板维度规范

### 3.1 模板维度

每条通知文案由四个维度共同选择模板：

| 维度 | 取值 | 决定什么 |
| --- | --- | --- |
| **时间关系** | `tonight` / `tomorrow` / `soon` / `now` | 用户读到的紧迫程度 |
| **呈现方式** | `general` / `rise` / `max` | "今晚有满月" vs "满月 18:42 升起" vs "食甚 21:17" |
| **发生时段** | `morning` / `night` | 晨前还是昏后，直接影响方位描述 |
| **半球** | `north` / `south` | 分至点的语义翻转 |

### 3.2 模板选择规则

1. 时间关系优先级高于一切：`tomorrow` 的事件永远不使用 `tonight` 模板，哪怕其他维度匹配。
2. 呈现方式由规则里的提前量决定：提前量 ≥ 12 小时用 `general`；提前量在事件形态时刻（升起/食甚/峰值）前 2 小时内用 `rise`/`max` 模板。
3. 半球只影响分至点类型；其他类型若南北半球描述不同（如"夏季大三角"的适用季节），由本地化文案按观测者纬度处理，不新增变体。
4. 每个类型×变体必须有回退模板：任一维度缺失时回退到该类型的 `general` + `tonight` 组合，禁止拼接出"将在今晚发生明天"这类矛盾文案。

### 3.3 文案要素

每条通知文案必须包含：事件名（本地化）、本地时刻（含时区）、观测地点名称。可选包含：方位/高度提示、持续时间、观测建议（如"选择东方开阔地平线"）。禁止出现："现在可看"（除非事件正在进行且在地平线上）、无时区的裸时刻、与观测点无关的全球性断言。

### 3.4 多语言

模板按 `zh-CN` 基线编写，其他语言复用同一维度矩阵。天体名称、事件名与文案模板分离，遵循 `specs/I18N-ARCHITECTURE.md` 的译名分层（稳定 ID / 原名 / 官方本地化名），不在模板里硬编码天体译名。

## 4. 本地可见性过滤规则

通知发出前必须通过本地可见性检查，全部离线完成：

1. **地平线检查**：事件主时刻（食甚、峰值、合相最近时刻、过境最高点）天体高度角低于用户规则中的 `minimumAltitudeDeg`（默认 5°）则降级或跳过。
2. **昼夜检查**：明亮天体（月亮、行星、卫星）的观测窗口按暮光（太阳高度 −6°～−18°）计算；白天时段的过境不提醒，除非用户单独订阅白天凌日。
3. **全球事件的本地化**：日食/月食、分至点按全球时刻计算，但"今晚""月升时"等时间关系变体必须按观测者位置重算；观测点不可见的日食降级为"天文事件记录"类信息通知，不进入提醒调度。
4. **位置变更失效**：观测位置或时区变化后，按位置相关的提醒全部重新计算并去重重排；与模拟时间严格隔离，始终使用设备真实时间。
5. **数据时效检查**：卫星 TLE、流星雨活动数据超出有效期时，对应类型的提醒注册停止并在设置页标示原因，不静默发送过期提醒。

## 5. 与现有实现的对接

### 5.1 数据契约扩展

`AstronomyEventKind` 从 7 值基线扩展到本目录的 22 值（旧值保留为别名）；`AstronomyNotificationRule` 增加 `variants` 屏蔽位（可选，默认全收），其余字段（`leadMinutes`、`minimumAltitudeDeg` 等）沿用现有契约，不改变既有字段含义。

### 5.2 提醒调度

- 继续使用 `reminderAgentManager` 日历型代理提醒，滚动窗口注册，遵守 API 26 起 64 条（API 25 及以下 30 条）配额；本目录类型数量远超配额，因此窗口内按"用户订阅优先级 + 事件罕见度"排序（日月食 > 冲日/大距 > 流星雨峰值 > 常规月相）。
- 每条提醒的 `kind` 携带本目录类型 ID，`wantAgent` 参数携带变体与路由信息，点击后按类型直达对应面板（日月食 → 天文计算食页面，卫星 → 卫星面板，流星雨 → 流星雨面板）。
- 代理提醒开放能力（AGC 权益 + Profile）未获批前，类型目录仅用于应用内事件列表和通知预览，不注册系统提醒；获批前不得把应用内提示描述为可靠后台提醒。

### 5.3 计算来源复用

| 类型组 | 复用命令 |
| --- | --- |
| 日月食 | `getEclipses`（含可见性信息） |
| 月相/超级月亮 | `getMoonPhases`、`getAlmanac` |
| 分至点 | 二十四节气计算的太阳视黄经 0°/90°/180°/270° 交节时刻 |
| 行星动态/合相 | `getPlanetTimeSeries`、`getObjectPositions`、`getRTS` |
| 流星雨 | `getMeteorShowers` |
| 彗星 | 现有彗星数据；最亮时刻计算作为缺口登记 |
| 卫星 | `getSatellites` + TLE 有效期状态 |

缺口（彗星最亮时刻、合相最近时刻的精确计算）在实施前登记到 `KNOWN-ISSUES.md`，不在本文档虚构已有能力。

## 6. 订阅模型与隐私边界

- 所有类型默认关闭；用户按类型或类型组开启，设置页展示下一次触发时间、已注册数量和配额余量，支持批量清除。
- 不新增任何联网、后台轮询或设备标识读取；位置数据仅用于本地可见性计算，不外发。
- 通知不用于营销或与应用无关的运营消息；代理提醒的使用持续符合华为"代理提醒"能力规范。
