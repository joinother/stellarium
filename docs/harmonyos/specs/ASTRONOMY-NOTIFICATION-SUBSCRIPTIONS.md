The loader caches successfully parsed month events by year/month, exact local-month start/end timestamps and language. Use it only after genuine catalog/resource updates, then explicitly refresh subscriptions; ordinary browsing does not invalidate. Each load returns a fresh generatedAt, and subscriptionCandidates still filters event times against real current time. Initial uncached month computation remains necessary.

Refresh requests blocked by another notification operation keep subscriptionRequested set. Status/authorization/manual-schedule/cancel finally blocks resume a pending refresh once the controller is idle; run completion also covers the Promise-finalization race. Background or preference failures retain pending work without self-retrying. Concurrent requests coalesce; no timer, polling or unconditional retry loop was added.

## Scheduling and failure semantics

- New installations default all categories off. Preferences retain the existing file/key, adding `satellitePassEnabled`, `digestEnabled` and `subscriptionsVersion:1`. Legacy manual preferences do not imply consent to automatic subscription and migrate category flags off while retaining quiet hours/lead.
- Astronomy queries device-local months over the next 45 days (at most 3 months); satellite queries a 48-hour window. Both use wall-clock time. At most six candidates per category are kept. Non-solar-term events fill the astronomy budget first, sorted by actual time; solar terms fill remaining capacity. Meteor catalog estimates remain estimates, not fabricated visibility claims.
- Quiet hours skip events rather than postpone them. Satellite lead time is 0–60 minutes; automatic astronomy events fire at their event time. Requests within 30 seconds of firing are skipped. Preferences/location changes remove no-longer-wanted subscription entries; replacement of a retained event uses the service's publish-before-cancel protection.
- Want metadata carries `subscription:'astronomy'|'satellite'`, but system query results are not relied on to return it. A private persisted journal restores ownership only after matching valid system ID and request fingerprint. Event keys include the subscription namespace, separating subscriptions from manual reminders. Disabling uses `cancelOwned(item)` to re-query and revalidate the fingerprint immediately before cancellation, including ID zero; never cancelAll. Cancellation errors are shown and retried on the next explicit refresh/foreground. Privacy withdrawal does not prevent cancelling disabled subscriptions.
- Every subscription publish passes a maximum of 24 active app reminders to the service. This is checked inside its serialized queue and counts manual reminders too. Unchanged dedup entries do not consume new capacity. Replacement needs spare capacity; budget failure preserves the old item. Official API ≤25 limit is 30; API 26+ is 64, but entitlement can make the actual quota zero.
- `1700002` stops the batch. With an empty system list, switches are rolled back and persisted off, with the actual error visible. Partially registered batches remain explicitly marked with failure; existing valid reminders are retained. Failed feed/list reads do not invent empty successful data or claim scheduling succeeded. A successful empty feed is shown as subscribed with no matching events.
- Foreground refreshes are coalesced. Preference/disable/location refresh increments a revision so a stale native fetch cannot publish. No cross-process transaction is claimed; in-flight OS publication cannot be undone atomically, and the next reconciliation repairs stale owned entries.

## Durable reminder ownership and legacy records

Real-device evidence from the parent: publication succeeds, while `getAllValidReminders()` omits `wantAgent.parameters`. This does not show that parameters are unsupported during publication or absent during a notification click. Full official MCP documents `js-apis-reminderagentmanager` and `js-apis-data-preferences`, and the local API 24 SDK, were checked again: WantAgent parameters/uri are API 12 fields; the query does not guarantee a complete echo of all publication fields. Actual click behavior remains a device verification item.

Service `configure(context:common.UIAbilityContext):void` only supplies context; it does not read storage or call reminder APIs. The controller constructor and authorized QAbility.routeCardWant now configure it. Other future service entry points must configure it before scheduling/listing. Storage is application-private Preferences file `stellarium_reminder_metadata_v1`, key `journal`, separate from notification settings. The versioned journal contains a monotonically increasing notification-ID high-water mark and at most 128 bounded entries. API 24 Preferences permits a 16MB value; the bounded journal is below that limit. This is a single-process serialized writer, not a cross-process database.

Publication first flushes a prepared record (system reminderId=-1), unique notificationId, normalized event key/signature/route and exact request fingerprint. It checks foreground/privacy again after persistence, publishes, reads back the actual ID/request, then flushes the ID binding before deleting any old reminder. Preparation failure causes no publication/cancellation. Post-publication binding/readback failure returns `ok:false,partial:true,reminderId,activeReminderIds` and preserves old reminders. A subsequent explicit operation can recover a prepared record only from a unique matching notificationId/fingerprint in the valid system list; an already-bound entry additionally requires the same reminderId. A mismatched/reused ID loses ownership and is never automatically cancelled. Missing required fingerprint fields fail closed. Failed preference writes are repaired from the last confirmed journal before proceeding.

Fingerprint fields are notificationId, reminder type, exact title/content, runtime target bundle/ability, calendar date/time (missing seconds normalized to zero), alarm hour/minute and repeat arrays. Timer remaining seconds are deliberately excluded because readback may be mutable; original requested duration remains in the persisted dedup/replacement signature. The service never reuses its persisted notification IDs. `list()` adds `ownershipFingerprint?:string`; unverified legacy records have `kind:'unknown'`, empty eventId and no subscription. Explicit user `cancel(id)` remains available; automatic cancellation must use `cancelOwned(item)`.

Existing legacy reminders with no journal are not silently adopted as subscriptions. A calendar candidate exactly matching the readback fields (ignoring only notificationId when comparing against the candidate's newly allocated ID) blocks duplicate publication with `legacy-reminder-unverified`; it does not cancel or claim the old reminder and does not report a successful subscription update. Different times, repeat settings, body or target ability are not treated as the same request based on title alone. Original subscription/manual origin and original eventAt/lead cannot be reconstructed reliably from an identical OS request, so user review is required. Parent's existing device IDs 2–7 were not touched. Unknown legacy reminders can remain when a category is disabled; no claim is made that these unclassified reminders were cancelled.

Publication continues to pass the complete supported parameters. It also mirrors the route into `skyinstrument://astronomy/reminder?notificationId=<id>&route=<encoded-json>`. QAbility validates and consumes this URI as a fallback, preserving eventId/eventAt even when the click has no parameters. It does not infer a calendar match: the normal Main exact-ID/time selection check still applies. No actual click or device operation was performed by this task.

## Native satellite dependency

Loader always sends `getSatellitePasses` JSON `{id,hours:48,limit:32,minElevation:10,visibleOnly:true,startJD}`. Native investigation confirmed the existing predictor mutates global simulation/Satellite state per sample and uses shared epoch/observer caches. The native handler therefore rejects explicit epochs with `reason:'explicit_epoch_prediction_unsupported'`; satellite subscriptions are unavailable until a genuinely nonmutating predictor exists. Never omit startJD or set the simulation clock as a fallback. The loader surfaces the rejection without retrying a legacy query. Satellite feed failures turn the subscription off, persist that state, and attempt to cancel only its owned reminders; cancellation failures remain visible and retryable. Astronomy subscriptions remain independent. Future supported responses still require matching satellite identity, fresh orbit/prediction data, visible future passes and unchanged observer snapshots.
