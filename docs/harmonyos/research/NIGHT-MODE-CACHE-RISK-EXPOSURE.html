夜间模式修复后的剩余风险敞口

桥的 consume-on-read 命令缓存没有全局版本号：旧快照可以被后来的逻辑请求当成新回包消费。

一句话：夜间模式的请求级缓存键已经把这个竞态封住；但桥本身仍按 cmd|arg 消费且没有 revision/TTL，其它使用固定 payload 的读命令（尤其 AstroCalcController / TimeController 的 getState('')） 仍可能把“切换前/修改前”的快照应用回来。

1风险存在点

ArkTS / UI 逻辑

  • 已隔离 MainWindowNativeNode 的 getState 带刷新序号
  • 已隔离 TimeStore 的 getNightMode 用入队 epoch 校验
  • 已隔离 NightModeStore 的 setNightMode 带 |epoch
  • 敞口 AstroCalcController 4 处 getState('')
  • 敞口 TimeController 1 处 getState('')
→

桥缓存（native）

  • key = cmd|arg，例如 getState|
  • consume-on-read：读到即删除
  • 没有 revision：无法判断快照年龄
  • 没有 TTL：旧结果可以一直留到下次同名请求
  • 轮询链放弃后，结果仍会写入缓存
→

Qt 渲染泵 / 引擎

  • 命令在 Qt 线程按队列执行
  • 长任务会阻塞队列（getMoonPhases 等）
  • 快照在“执行那一刻”产生
  • ArkTS 侧的轮询预算约 1.5s，超时就放弃
关键错位：ArkTS 的 epoch 只能证明“我什么时候发起/消费了这个请求”， 不能证明“这份快照是什么时候产生的”。只要旧快照能被同一个 cmd|arg 再次消费， 版本判断就会失效。

2触发场景（时间线）

t0

请求 A 入队

getState| 被 AstroCalc 或 TimeController 发出；桥返回 pending。

t0 + 1.5s

轮询链放弃

Qt 线程被长任务卡住，ArkTS 不再轮询；A 之后才执行完。

t0 + 2s

状态被修改

用户改 FOV / timeRate / 图层；引擎状态已经变化。

t0 + 3s

请求 B 消费旧缓存

另一个 getState| 调用命中 A 留下的快照，读到即删除。

t0 + 3.1s

旧值写回 UI

FOV / timeRate / actionShow_* 回到修改前；用户看到回退/闪烁。

最小触发条件：轮询链超时放弃 + 之后有另一个同名 cmd|arg 请求 + 两者之间发生过状态修改。三个条件同时成立时，旧快照会被当成新回包。

3当前边界：哪些已封住，哪些仍暴露

路径 缓存键 状态 仍可能受影响的字段
MainWindow getState getState|<nonce> 已隔离 夜间模式及其它 getState 字段
TimeStore getNightMode getNightMode| + 入队 epoch 已隔离 夜间模式
NightModeStore setNightMode setNightMode|true|<epoch> 已隔离 夜间模式回执
AstroCalcController getState('') getState| 敞口 FOV、timeRate、actionShow_* 等
TimeController getState('') getState| 敞口 同上，且与 AstroCalc 共享同一个键
未来新增读命令 取决于 payload 需约定 只要使用固定 payload，就会重复同类竞态

4根治方向

方案 A：native 状态 revision（推荐）

每次 mutation 递增 revision；所有回包带 revision。调用方拒绝 reply.revision < lastKnownMutationRevision 的快照。与命令名、字段无关，覆盖所有读路径。

方案 B：mutation 执行时清读缓存

在 setNightMode / setFOV / setTimeRate 等 mutation 执行时清掉 getState|、getNightMode| 等读缓存。实现小，但需要维护 mutation 列表。

方案 C：所有逻辑请求带唯一键

像现在的 MainWindow getState 一样，每个逻辑请求用 nonce/epoch 作为 payload， 旧快照永远对不上新键。改动集中在调用方，但每个新读命令都必须遵守。
