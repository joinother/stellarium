# Project Conventions

- Server operations follow `docs/harmonyos/server/SERVER-SECURITY.md`. Use `scripts/resource-server-cli.sh` for routine diagnostics. Workbench can reuse a session across requested usernames: always verify the actual OS user before executing commands. Do not silently escalate to root, broaden RAM permissions, expose public ports, or copy credentials into commands or the repository.

- Test application navigation, selections, options, and feedback through the existing semantic CLI first. Inspect both the native command catalog and ArkUI-specific command handlers. Do not use coordinate clicks for ordinary navigation; reserve screenshots/layout inspection for visual verification and touch injection for explicit hit-testing/gesture tests. Record missing UI commands instead of silently replacing them with coordinate automation. Follow `docs/harmonyos/DEVELOPMENT-MCP-WORKFLOW.md`.

- Content involving China, including maps, geographic scope, political terminology, regional names, and cultural descriptions, follows official Chinese terminology and geographic presentation requirements.
- Use official Chinese names for ethnic groups and administrative regions. In particular, use “西藏自治区”“中国西藏”和“藏族” where those concepts are intended; never present Tibet as an independent country or political entity.
- Treat cultural-distribution maps as cultural research overlays, not political-border maps. They must not alter, omit, or imply a different representation of China's territorial scope. Use “中国台湾地区”“中国香港特别行政区”和“中国澳门特别行政区” in Chinese UI text where applicable.
- For Chinese ethnic-minority and regional history, distinguish historical source wording from the application's own description, retain neutral scholarly attribution, and avoid unsupported political or ethnic generalizations.
- Do not present source authors' first-person wording as if it belongs to the user. In localized sky-culture descriptions, identify the original author or use a neutral attribution while preserving the source meaning.

- **Long-running refactor queues run autonomously, without checkpoint reports between slices.** When the user has approved a multi-slice plan (for example `docs/harmonyos/research/ARKTS-PAGES-REFACTOR-PLAN.md` §13), finish one slice and immediately start the next one in the same turn — build, verify, test, CHANGELOG and commit included. Do not end a turn with a summary and a plan for the next slice, and do not ask the user to confirm before continuing. Stop only to (a) request a decision that genuinely requires the user, (b) report a blocker, or (c) when the whole queue is finished. Progress belongs in the CHANGELOG and `§13` of the plan document, not in a per-slice status message.

- **ArkTS UI structure (post `pages/` refactor).** `harmonyos/ets-source/pages/MainWindowNativeNode.ets` is now only the page shell/glue: the root `Stack`, responsive layout dispatch, panel wrapping, Dock hit layer, overlays, lifecycle and bridge calls. Panel bodies live under `panels/panels/**`, shells under `panels/shell/**`, other domains under `panels/<domain>/**`; observable state lives in `state/*Store.ets` (`@Observed` classes) held by the host as `@State` and consumed by children via `@ObjectLink`/`@Prop` (V1 only — do not mix V1/V2). Two rules that bite: a host `@Builder` must never be passed into a child component (renders the page → whole app exits; plan §13.1 rule 9), and `floatingPanel`/`compactPanel` deliberately stay host `@Builder`s because their body calls `this.panelContent()`. `.id()` string anchors are a cross-session contract — run `node scripts/check-ohos-ui-contract.mjs` before finishing any UI change; never rename or drop them.
